# USB Display Current Project State

## Overview

USB Display is a native macOS 14+ SwiftUI application for displaying a USB-connected iPhone or iPad. Version 0.3.0 uses a standard Xcode app target, shared scheme, unit-test target, project-owned bundle metadata, and camera-device entitlement.

Capture uses public AVFoundation and CoreMediaIO APIs. A separate read-only client of the local usbmuxd/lockdownd protocols identifies product models. No companion app, Xcode installation, private Apple framework, recording, audio capture, remote transmission, or mobile input control is required.

## Current Capabilities

- Enables wired CoreMediaIO screen sources and disables wireless discovery. Accepts eligible external muxed Apple devices even when their public transport type is `Other`.
- Shares one device catalog across SwiftUI `WindowGroup` windows, with at most one window per selected device. Left-click switches the current window or focuses an existing owner; `Open in New Window` preserves the existing multi-window route.
- Gives each window an independent capture session, retry lifecycle, connection status, sidebar state, preview ratio, and ordinary-window geometry. `AppModel` owns device selection and renews its request on selection changes and stop/restart. Snapshots carry request identity, stream identity, and increasing sequence numbers; obsolete or out-of-order deliveries cannot overwrite the current selection or status. Closing a window releases only its session.
- Retains the compatible `AVCaptureVideoPreviewLayer` path. Each window owns one persistent preview view and layer, including across sidebar, titlebar, safe-area, and full-screen changes. Ordinary windows with a known source ratio use aspect fill to cover the small remainder from AppKit frame rounding; full screen, transitions, and unknown geometry retain aspect fit.
- Hosts the preview, SwiftUI device list, connection overlay, and control backgrounds in an explicit AppKit container. The preview no longer participates in `NavigationSplitView` sizing.
- Uses a responsive 30% sidebar / 70% content split when no active source ratio is available, including no-device, selection, and connection placeholders. Empty windows resize freely within screen bounds and have a nominal 720-by-480-point minimum, capped by the screen; AppKit may add native toolbar height. Late narrow frame restoration is repaired synchronously. Hiding the sidebar gives the content the full width.
- Stores the empty-window frame separately from the preferred video rectangle for each window. A connected source restores proportional video sizing and its smaller minimum; disconnecting restores the empty layout. Changes arriving during a drag wait for release, and full-screen transitions retain ordinary geometry.
- Commits the complete outer frame and child frames together with implicit Core Animation actions disabled. Child frames use the actual window frame accepted by AppKit, including its quantization. Expanding controls reserves space once before revealing them; collapsing controls releases space after the animation. There is no timer-driven outer-frame animation, preview snapshot substitution, or delayed resize correction.
- Adds sidebar space to the left and titlebar space above the preferred preview rectangle. A preview that fits the current screen keeps its size; controls overlay along axes where the combined dimensions cannot fit. An oversized preview scales proportionally to the screen without replacing its preferred size, so returning to a larger display restores that size. Screen and display-parameter changes during a drag or full-screen transition are applied after it ends.
- Keeps preferred geometry in memory per window. User movement translates it; live resize and valid ordinary non-live resizes replace the preferred size, including native Zoom during control animation. App-owned layout, screen fitting, and full-screen transitions do not replace that preference. Source rotation preserves the preferred height; screen fitting is computed separately from the preference.
- Constrains AppKit resize proposals through a per-window `ResizeSession`, freezing the starting frame, source ratio, actual external control insets, and screen size for the gesture. Left/right edges follow width, top/bottom edges follow height, and corners project raw proposals onto the aspect-ratio line. The strategy is selected once from the starting pointer or first meaningful raw proposal; accepted sizes never feed back into axis selection. AppKit retains control of the opposite edge/corner and origin.
- Suspends hover and source-ratio publication during live resizing. A control fade can finish during a drag, but its space remains reserved until release; cleanup preserves the user-resized preview. Source/configuration changes are applied after release. Shadow invalidation happens at chrome boundaries or resize completion, not each resize proposal.
- Animates the app-owned sidebar, divider, and titlebar background with a shared 200-millisecond ease-in/ease-out timeline and up to 8 points of travel. Reduce Motion keeps the fade and removes travel. A window display link updates these views and the preview mask, never the video window frame or native window buttons. Rapid reversals retarget from current presentation, and metadata updates do not restart the timeline. Empty content follows the animated split and ends at 30/70.
- Preserves SwiftUI's window lifecycle and forwards its original window delegate behavior. A standard image-based navigational `NSToolbarItem` in the native unified-compact single-row toolbar toggles the AppKit sidebar and exposes `Show Sidebar` / `Hide Sidebar` labels. AppKit generates and sizes the button with its default appearance; there is no custom button view, bezel, fixed size, opacity, or transform. Ordinary compact mode hides the native window buttons; reveal unhides them before showing the toolbar. App code does not animate or overwrite their opacity, so they remain measurable throughout AppKit's deferred toolbar layout and the sidebar item stays clear of the traffic lights.
- Keeps native window buttons when controls are visible. Compact mode hides toolbar/buttons/background; an 8-point top region reveals the titlebar, with an 8-point bridge and a 0.5-second hide delay. Local events require no global monitor or Accessibility permission for the application itself.
- Keeps the window and app-owned container transparent at all times. Black is drawn only inside the preview surface. Compact mode uses an explicit continuous-outline alpha mask for the complete preview, including live video and its black backing. A persistent `CAShapeLayer` replaces implicit `cornerRadius` clipping; the status overlay uses a separate mask with the same geometry. Expanded controls draw their own backgrounds.
- Disables the system window shadow in compact mode so it cannot expose the rectangular window behind the rounded preview. Expanded controls restore the original shadow setting. The native window style remains intact for keyboard focus, window buttons, and macOS 14 compatibility.
- Uses the complete full-screen surface with aspect-fit black bars. The SwiftUI window owner uses `windowToolbarFullScreenVisibility(.onHover)` on macOS 15+, with AppKit `autoHideToolbar`/`autoHideMenuBar` presentation options supporting macOS 14. AppKit owns full-screen toolbar reveal, hiding, timing, and traffic-light animation. App code does not change native toolbar visibility or button opacity during full-screen hover/sidebar updates, and there is no manual full-screen toolbar timer. The leftmost 8 points reveal a temporary sidebar overlay; the toolbar button also toggles it. Leaving the sidebar and top control region hides the overlay after 0.5 seconds. The sidebar and divider follow the native unobscured content rectangle, clearing the actual toolbar height while it is shown and reclaiming that space when hidden. Those toolbar-inset notifications update only visible sidebar/control frames, without updating the video layer; unchanged toolbar labels are not reassigned. Full-screen controls do not resize or shift the video, and each full-screen entry starts with the sidebar hidden. Exiting restores ordinary geometry and the previous sidebar state, adapting to any source rotation that occurred during full screen.
- Queries only USB `ProductType` and `DeviceName` off the main thread. Exact names must be unique in both complete capture and USB snapshots. Duplicate names are unresolved, and stale query generations cannot update a replaced device list.
- Automatically matches exact USB product types against 164 bundled reference profiles: 60 iPhone and 104 iPad identifiers. Apple Simulator geometry is extended through explicit DeviceKit hardware groups and cross-checked with BezelKit. Radius scales by the displayed short side and uses the same normalized value in either orientation.
- Uses standard SwiftUI `Button` device rows with selected styling and a context menu; secondary click alone does not select a device. Shows the device name as each row's primary label and the resolved model, such as `iPhone 16 Pro`, below it in smaller secondary text. Unlisted products fall back to ProductType. The subtitle is omitted when model resolution falls back to the same device name, avoiding duplicate lines. Corner and identification-status annotations remain hidden. Unknown or unresolved products still use zero custom radius. Manual sliders are removed; legacy preference data is preserved but never applied.
- Reports no-device, connecting, unlock/trust, connected, interrupted, occupied, unavailable, permission-denied, and failure states. `ContentUnavailableView` presents selection, unavailable, and failure states with the existing guidance; connecting retains `ProgressView`. Capture retries remain local to each window and use capped delays; the number of attempts is not limited. Interruption invalidates startup confirmation, and recovery revalidates the input/running state before publishing connected status. Permission completion re-evaluates only the current active request.
- Resolves titlebar and separator layer colors under the view's `effectiveAppearance` in `viewDidChangeEffectiveAppearance`. Full-screen entry/exit failure callbacks forward to the original delegate and restore layout, animation, and hover state from the actual window mode.

## Architecture

- `DeviceCatalog` owns capture discovery and an independent `DeviceIdentityService` refresh lifecycle. Equal raw discovery snapshots are deduplicated before identity work starts; names sort deterministically with an ID tie-breaker. The five-second identity refresh and conservative complete-snapshot matching remain in place.
- `USBDeviceInfoClient` implements bounded local protocol I/O. `DeviceIdentityMatcher` performs conservative name association. [Protocol and compatibility details](usb-device-identification.md).
- `DisplayWindowScene`, `DeviceWindowRegistry`, and `AppModel` retain SwiftUI lifecycle, window ownership, device selection, and per-window capture state.
- `CaptureCoordinator` provides the serial queue boundary. `CaptureStateMachine` owns request/stream generations, permission, reconnect, stabilization, and retry transitions with injected event and delay scheduling. `AVFoundationCaptureDriver` retains one discovery session and one capture session per window, and provides the narrow AVFoundation operations and notifications. Tests use controlled drivers and clocks rather than physical devices or exposed private state.
- `WindowSurfaceLayout` calculates outside-versus-overlay chrome, local child rectangles, and the balanced placeholder split. `WindowGeometryState` separates preferred preview geometry from current fitted placement. `ContentView` excludes a retained capture ratio while the connection status is not connected.
- `WindowLayoutHostView` remains the sole owner of layout state, stable children, chrome reservations, and synchronous geometry commits. `SidebarToolbarDelegate` owns the toolbar and standard image item's target/action, `WindowEventBridge` owns AppKit notifications/KVO/event monitoring and delegate forwarding, and `WindowHoverScheduler` invalidates delayed hover work across cancellations and mode changes. `ResizeSession` provides gesture-local proportional sizing. `WindowChromeAnimator` owns a cancellable display-linked timeline with an injectable clock; the host separately tracks target controls and reserved geometry. Its display-link relay does not retain the host.
- `PreviewHostView` synchronizes preview-layer bounds, its own corner mask, and backing scale in nonanimated transactions, including direct frame/bounds changes before deferred layout. `RoundedContentMask` derives a complete `CGPath` from SwiftUI's continuous `RoundedRectangle`, reuses one shape layer per masked surface, and rebuilds the path only when size or radius changes. Settled expanded/full-screen states remove the custom mask. During a control transition a tiny nonzero endpoint radius preserves continuous-path topology, and the preview/status masks share the same progress. Frame/bounds callbacks are coalesced during an explicit geometry application; unchanged geometry and video gravity are not reassigned. The half-second timer only detects source aspect changes. `PreviewAspectRatioTracker` resets `StableAspectRatio` per request/stream source, preserving the session and preview layer. The first usable ratio is immediate even when two devices have equal ratios; later changes require two consistent samples. Callbacks carry the source identity and are validated by the model; geometry transitions discard pending candidates.
- `DisplayCornerProfileResolver` validates and loads the bundled JSON catalog once, then resolves exact USB product types. Invalid catalogs fall back to unmatched profiles.
- `script/update_device_profiles.py` reproducibly generates the offline catalog, source audit, and bundled MIT notices from pinned and hashed inputs. Unreviewed source conflicts stop generation. [Sources and update workflow](device-corner-profiles.md); [complete model catalog](device-corner-catalog.md).

## API and Compatibility Boundaries

Wired mobile screen sources expose opaque public formats with `0 x 0` dimensions and no public frame-rate range. The app sets no session preset and makes no native-resolution, latency-control, or sustained-frame-rate claim. End-to-end latency requires external measurement.

The previous `AVCaptureVideoDataOutput` / `AVSampleBufferDisplayLayer` implementation was removed after the physical iPad source rejected startup with `!dev`; direct preview remains the supported path in this project.

Opaque capture model strings such as `iOS Device` do not identify the physical product. The isolated read-only USB query supplies exact ProductType values for catalog lookup. usbmuxd/lockdownd are not an Apple-guaranteed public SDK. Identity failures remain independent of capture. There are no pairing changes or authenticated session requests.

Rounded corner values are traceable Simulator display-reference measurements, not live physical hardware measurements. Older square displays can also use a zero radius corroborated by DeviceKit and BezelKit. The conflicting iPad Air 3 profile is explicitly resolved to zero; known BezelKit mapping errors are corrected or excluded. iPhone 16 Pro and iPhone 17 Pro share 62 / 402 in the source; iPhone 17 Pro Max uses 62 / 440. The app does not fabricate differences, infer a specific model from a name/aspect ratio, or read simulator files at runtime.

- Deterministic capture coverage includes equal-ratio switching, A-to-B-to-A, stale snapshots/events, out-of-order publication, stop/restart, interruption during startup confirmation, automatic recovery, permission completion, reconnection, occupied/suspended states, and configuration failures. USB identity tests wait for bounded completion/publication signals; socket deadline and cancellation checks remain real local-socket tests.
- Window regression coverage includes ordinary non-live resize, resize during chrome animation, failed full-screen entry/exit with original-delegate forwarding, smaller-screen fitting and restoration, deferred screen changes, resize-before-screen notification ordering, appearance callbacks in both directions, and stale hover cancellation.
- Existing coverage retains stable preview-layer identity, continuous corner alpha, all eight resize strategies, gesture freezing, sidebar animation/retargeting, full-screen toolbar noninterference, balanced placeholders, and independent windows. Rendering checks use synthetic changing frames in real AppKit/SwiftUI view hierarchies; they do not establish WindowServer frame pacing for live video.
- Audit validation baseline: 100 Debug tests passed, zero failures and zero skips. - Live iPad acceptance covered changing preview content, the selection empty state and connecting progress indicator, secondary-click preservation, existing-window routing, sidebar buttons, native Zoom, and full-screen entry/toolbar hiding/exit. ## Constraints and Outstanding Validation

- Current physical acceptance includes a live iPad Pro (11-inch, M4) preview, the native selection state and row/context-menu routing, sidebar controls, native Zoom, and a full-screen entry/hide/exit round trip. Repeated drags from all eight handles, continuous fast reversal, physical 20-cycle sidebar toggling, and titlebar-hover/resize interleaving remain incomplete. No continuous WindowServer recording has established frame-by-frame smoothness or freedom from a one-frame flash.
- Empty-state narrow restoration is covered by the balanced split and minimum-size repair. On the final relaunch, the UI remained connecting for approximately two minutes before AVFoundation reported startup; discovery then changed from one device to none and back to one, and the final selected iPhone displayed live content. The startup wait was not isolated to permission, device, or system state. Controlled startup latency and first-frame behavior remain outstanding; the process-running check does not prove video readiness.
- Real pointer drags from all eight handles, fast consecutive drags, and hover/resize interleaving need valid intermediate pointer events and physical acceptance. Delegate proposals and endpoint screenshots cannot establish drag smoothness or anchoring.
- WindowServer frame-by-frame recording of actual video over contrasting desktop content remains separate from the AppKit bitmap tests. JPEG-only UI screenshots cannot independently prove alpha or absence of a one-frame flash.
- The 164 catalog entries are metadata/test coverage, not physical validation of 164 devices. Six uncorroborated BezelKit identifiers remain excluded; future rounded models require measured geometry and reviewed mappings. Older-device metadata does not guarantee USB capture compatibility.
- Physical iPhone 17 Pro / Pro Max, additional iPad models, rotation, hot unplug/replug, external-screen removal/restoration, and concurrent capture with multiple connected devices remain hardware checks. Reduce Motion and native drag anchoring on all handles also require runtime acceptance. Fixtures do not count as physical runs of unavailable products.
- macOS 14/15 toolbar behavior, forced physical interruption/occupied-device recovery, permission denial and TCC relaunch behavior, a 30-minute multi-window soak, production signing, notarization, distribution, and external performance measurements remain outstanding. There is no new permission-settings retry action or app-activation recheck in this change.
- Local builds are ad-hoc signed; rebuilding can require camera permission again. Xcode disables hardened runtime for the Debug ad-hoc build.
- DRM-protected content may appear black; the app does not bypass platform protections.
